# Calendar dependency validation — 2026-11-03

For v2.1.0, the owner approved a minimal security refresh after the release audit found new high-severity advisories. Electron is now pinned to **44.10.1**, with observed Chromium **152.0.7977.169** and bundled Node **24.22.1**. Build Node **24.21.0**, npm **11.19.0**, electron-builder **26.17.0** and @electron/fuses **2.1.3** remain unchanged. Compatible lockfile-only updates select Undici **6.29.1** under node-gyp and **7.30.1** under @electron/get; no overrides or major dependency upgrades were added.

The refreshed `npm audit --audit-level=high` passes with **0 high/critical and 16 moderate affected-package entries**. Electron's [compromised-certificate mitigation](https://github.com/advisories/GHSA-jr5w-w6x2-84p9) matters to the shipped application because it loads Calendar over Chromium HTTPS; origin restrictions and renderer isolation do not replace TLS server authentication. The patched runtime includes the upstream mitigation. Undici is build/download tooling rather than an application npm runtime dependency. Its compatible updates include the [TLS options fix](https://github.com/advisories/GHSA-2m5v-pch6-74hx) and [excessive content-encoding fix](https://github.com/advisories/GHSA-xjj6-f33q-929c). Individual vulnerable downloader paths were not exploited locally; patched versions and the audit are the verification substitute, followed by package smoke checks.

Remaining moderate entries concern fast-uri and minimatch and their build-tool dependants. They remain documented limitations; the high-severity release gate was retained. The runtime/SDK/base used for Flatpak is 26.08 and its actual commits are recorded in BUILDINFO.json. Package staging strips group/other write and special permission bits from the upstream Electron archive before making root-owned RPM files.

## Historical validation — 2026-10-11

Pinned build environment: Node 24.21.0 / npm 11.19.0. Electron 44.7.0 embeds Chromium 152.0.7977.130 and Node 24.21.0, observed from the downloaded runtime. electron-builder 26.17.0 and @electron/fuses 2.1.3 are exact development pins. Lockfiles are committed and ordinary builds use `npm ci`.

The refreshed audit gate `npm audit --audit-level=high` exits successfully: **0 high/critical, 8 moderate affected-package entries**. These entries propagate one underlying [sprintf-js advisory](https://github.com/advisories/GHSA-hp3w-g68c-fv3c); all are development/build dependencies. The relevant path is electron-builder → app-builder-lib → @electron/get 3.1.0 → global-agent 3.0.0 → roarr 2.15.4 → sprintf-js 1.1.3. Additional builder package entries propagate the same dependency issue. No patched sprintf-js release is listed. A forced builder downgrade is not an acceptable universal remediation.

The precision parsing issue remains in sprintf-js. It needs an attacker-controlled format string to reach numeric formatting. The wrapper ships no renderer Node bridge and packages no npm runtime dependency tree; no shipped-app exploit was established. This is an exposure assessment, not a declaration that build tooling is immune.

A targeted compatible lockfile update selected http-cache-semantics 4.3.0 through cacheable-request's existing range: electron-builder → app-builder-lib → @electron/get 3.1.0 → got 11.8.6 → cacheable-request 7.0.4 → http-cache-semantics 4.3.0. npm no longer flags this node, but the [cross-user cached-response advisory](https://github.com/advisories/GHSA-ch52-4w7c-c8xp) still lists no patched version. A version outside the database range alone does not prove the security defect fixed. The wrapper does not implement a shared multi-user HTTP cache; this library is in build/download tooling. A synthetic library probe confirmed the max-stale behavior remains in 4.3.0: a shared response with Set-Cookie yielded maxAge=0 while a large max-stale directive was accepted without revalidation. The build downloader forwards got options without enabling its HTTP cache by default; got's default cache is undefined. This does not demonstrate a cross-user cache in this template. Treat the library issue as unresolved and continue tracking upstream resolution.

Calendar's refreshed lockfile was independently installed and audited with the pinned tools. Runtime versions, got's default cache and the max-stale reproducer were checked locally; the underlying cache defect still reproduced. Every other generated application needs its own audit. Historical zero-finding statements in immutable release notes describe older runs, not this result. Build metadata records actual runtime, tool, runner and packaging-binary versions/digests; locked dependencies do not guarantee bit-for-bit identical artifacts.
