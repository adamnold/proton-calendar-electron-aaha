# Configuration v3 migration

This is a breaking template release. Version 2 host-based configurations are rejected with migration instructions. Review every required flow and replace `trustedNavigationHosts` / `trustedAuthHosts` with `trustedNavigationOrigins` / `trustedAuthOrigins` containing exact HTTPS origins, for example `https://app.example.com` or `https://app.example.com:8443`. Sibling subdomains and different ports are separate identities. The starting URL must match a navigation origin. Permission lists also contain exact HTTPS origins. Empty lists deny access.

Do not mechanically copy broad parent-domain permissions. Authentication and notification rules require service-owner testing. Origins cannot contain credentials, paths, queries or fragments.

Omitting `blockedHosts` inherits the shared privacy defaults. An explicit list replaces the defaults; `[]` explicitly disables that blocklist. Blocking is a privacy mitigation and is not proof that the upstream service or Chromium makes no other network requests.

Calendar 2.0.0 intentionally renames the repository, product, executable and application ID. The per-user AppImage installer copies `Proton Calendar` to `proton-calendar-electron-aaha` only when the new profile does not exist, retaining the original. Profiles, migration and purge share the absolute XDG configuration root. Normal uninstall preserves profiles. See README.md for retiring the old installation without purge before installing the renamed application; old receipts/custom roots are not discovered by the new repository name. Profile-copy regression tests use disposable data; signed-in session continuity remains pending.

Calendar 2.1.0 adds native RPM and Flatpak packages. Before switching a per-user AppImage install to RPM, quit the application and use its original checkout's `bash uninstall.sh` **without `--purge`**, including its custom install root if applicable. This preserves data and removes per-user desktop entries that could shadow the RPM desktop entry. RPM installs under `/opt` and uses the same native `proton-calendar-electron-aaha` profile as AppImage. Its root package hooks never inspect or migrate user homes. To migrate an old `Proton Calendar` profile, run the existing per-user installer before the first new native launch; installing an RPM alone does not perform that migration.

Flatpak has a separate profile at `~/.var/app/com.adamandhisagents.protoncalendarelectronaaha/config/proton-calendar-electron-aaha` and requires a fresh sign-in. It does not copy the native profile. Quit and remove the previous format's desktop integration when switching formats; choose one format to avoid duplicate launchers. Normal RPM removal and Flatpak uninstall preserve application data. Updates use a newly downloaded and authenticated package; no package repository, Flatpak application update remote or automatic updater is configured. See README.md for commands.

Old setuid sandbox helpers are not preserved during upgrades. Native RPM and AppImage hosts that prohibit unprivileged user namespaces must have their administrator enable a supported sandbox configuration; this template supplies no unsandboxed fallback. `AAHA_SKIP_SANDBOX_SETUP` has been removed. Flatpak uses its own launcher with Zypak directly on the native binary, rather than the host namespace preflight.

Generated apps must configure their own release key and refresh their own lockfile. Template signatures do not authorize application releases. Old release artifacts remain immutable; publish a new app version containing the changes.
